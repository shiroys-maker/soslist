# SOSList 予約データの保全・復元手順

対象: Google Cloud project `sos-list-4d150` / Firestore `(default)` / 東京 `asia-northeast1`。
2026年9月12日に設定。アプリのGitバックアップと、運用中の予約データのバックアップは別物として管理する。

## 保全設定

| 機能 | 設定 | 用途 |
|---|---|---|
| 毎日のバックアップ | 毎日1回、30日保存 | 日単位で過去のデータを戻す |
| 毎週のバックアップ | 毎週1回、14週間保存 | 遅れて気付いた誤削除・破損に対応 |
| 時点復元（PITR） | 7日間、1分単位 | 誤操作直前の状態を取り出す |
| データベース削除保護 | 有効 | データベース全体の誤削除を防ぐ |

Google側で動作するためMacの電源・Wi-Fiに依存しない。バックアップの実行時刻はGoogleが決め、指定できない。毎週の設定は日曜（UTC基準）。
初回バックアップの作成は定時処理待ち。設定前の30日・14週間分を遡って作成する機能ではない。PITRも有効化後に履歴が蓄積するため、直ちに過去7日すべてを戻せるわけではない。実際に指定できる最古時刻は `earliestVersionTime` で確認する。

データベース全体が対象なので、`appointments` 内の予約・メモ等と、同じデータベース内の他のコレクションも保全する。Firebase Storage内のPDF・音声、Authenticationの利用者情報、Firebase Security Rulesは別管理。データベース削除保護は個々の予約の削除までは防がない。

## 費用の目安

9月12日23:27 JSTの容量統計は14,416,986バイト（約14.4MB、0.01343GiB）。東京リージョンのUSD通常料金は、PITRが0.195ドル/GiB月、バックアップが0.038ドル/GiB月。
同じ容量が続き、毎日30世代と毎週14世代が揃った場合は、追加月額約0.025ドル（丸めて約0.03ドル）。税、通貨換算、将来のデータ増加は別。復元・クローンは使用時に別課金。今回の容量のクローン処理単価による試算は約0.00345ドルで、検証用の読み取りと一時保存は別。

計算: `容量GiB × (0.195 + 0.038 × (30 + 14))`。
これは費用の上限設定ではなく、現在の容量からの見積もり。

## 設定と作成済みバックアップの確認

Google Cloudコンソールで、対象プロジェクト → Firestore → `(default)` → 災害復旧を開く。
設定が有効であることに加え、バックアップ一覧の作成日時・有効期限・状態を確認する。

CLIによる読み取り例:

```sh
gcloud firestore databases describe --project=sos-list-4d150 --database='(default)'
gcloud firestore backups schedules list --project=sos-list-4d150 --database='(default)'
gcloud firestore backups list --project=sos-list-4d150 --location=asia-northeast1
```

## 誤削除・誤更新時の復元

1. 問題が発生した時刻と対象範囲を特定する。更新を続ける処理がある場合は、その処理の停止範囲を判断する。
2. 直近の誤操作なら、PITRの最古時刻以降から、問題が起きる前の1分単位の時刻を選ぶ。古い問題なら、作成済みの定期バックアップを選ぶ。
3. 本番 `(default)` を上書きせず、同じプロジェクト内の新しい名前のデータベースへクローンまたは復元する。
4. 対象予約のID・日時・メモ・関連フィールドを確認する。復元元時点の本番と復元先の件数・内容の一致も確認する。
5. 本番に戻す前に、対象範囲と復元後の正しい状態を具体的に確認する。個別復旧なら対象フィールドだけを戻し、その後の正常な更新を消さない。全体切替なら認証・Rules・索引・PDF参照・アプリの接続先も別途検証する。
6. 復旧結果を確認し、検証のためだけに作成した一時データベースを削除する。本番の削除保護は維持する。

現在インストール済みの古いgcloudは `databases clone` に未対応だったため、今回の検証は公式REST APIを使用した。手順を実行する際は利用可能なコンソールまたは現行CLI/APIを使う。操作開始の受付だけで完了とせず、長時間オペレーションの成功と復元データを確認する。

今回の設定作業では本番の予約を書き換える復元は実施していない。災害時の本番書き戻しは、対象と時点を確認してから行う。
